# Выбор стека и его обоснование

Требования к стеку из задания: backend на Python, Go или Node.js (предпочтительно); frontend на Vue или React; реляционная СУБД (предпочтительно PostgreSQL); быстрый локальный запуск; внешние сервисы можно заменить заглушками.

Главный критерий выбора — рискованные места задания №9 (см. `docs/acceptance.md`, раздел 5): гонка за последнее место, идемпотентность, повторный чекин, письма «ровно одно», live-счётчик, перезапуск сервера. Стек должен закрывать их **средствами БД и стандартными механизмами**, без дополнительной инфраструктуры.

Статус: решения приняты до написания кода и ещё не проверены реализацией. Если реализация покажет проблему, изменение и причина будут записаны в журнал разработки.

## СУБД: PostgreSQL

Задание прямо предпочитает PostgreSQL, и его возможности напрямую закрывают риски:

- **Гонка за последнее место** — `SELECT … FOR UPDATE` на строке события сериализует регистрации, отказы и продвижение очереди внутри одного события, не блокируя другие события.
- **Повторная регистрация** — уникальный индекс (событие, email) и `INSERT … ON CONFLICT` — защита на уровне БД, даже если проверка в коде пропущена.
- **Повторный чекин** — условный `UPDATE … WHERE checked_in_at IS NULL RETURNING` атомарен без явных блокировок.
- **Письма без дублей** — уникальный ключ идемпотентности в outbox + `ON CONFLICT DO NOTHING`; отправитель берёт письма через `FOR UPDATE SKIP LOCKED`, поэтому два экземпляра не отправят одно письмо дважды.
- **Live между процессами** — `LISTEN/NOTIFY` доставляет сигнал «счётчики изменились» без отдельного брокера.
- **Время** — `timestamptz` хранит моменты в UTC.

**Отклонено:** SQLite — нет блокировок строк и `SKIP LOCKED`, запись блокирует всю базу; конкурентные тесты на ней ничего не доказали бы о поведении в PostgreSQL. MySQL 8 — тоже подходит (есть `FOR UPDATE SKIP LOCKED` и `ON DUPLICATE KEY UPDATE`), но нет аналога `LISTEN/NOTIFY` — для live понадобился бы отдельный канал; задание к тому же предпочитает PostgreSQL.

## Backend: Python + FastAPI

- **Язык.** Python входит в предпочтительные варианты. Версия — 3.14 (`requires-python = ">=3.14"`): такой интерпретатор пользователь установил и выбрал при создании `backend/` через uv. Зависимости и lock-файл — `backend/pyproject.toml`, `backend/uv.lock`.
- **Асинхронность.** Экран организатора держит открытое SSE-соединение. В асинхронном фреймворке оно стоит одну корутину, а не поток или процесс воркера; десятки открытых вкладок не занимают пул.
- **Обычные эндпоинты** пишутся синхронно (FastAPI выполняет их в пуле потоков) — так проще и надёжнее работать с транзакциями и блокировками.
- **Pydantic** — валидация входных данных и понятные ошибки 422 без ручного кода.
- **OpenAPI / Swagger UI** (`/docs`) генерируется автоматически — API можно проверить руками без frontend, что помогает доказуемости.

**Отклонено:**
- *Django + DRF* — ORM, админка и аутентификация из коробки, но для SSE нужны ASGI и Channels или ручные обходы; большая часть фреймворка (шаблоны, админка, формы) здесь не нужна.
- *Flask* — синхронный: каждое SSE-соединение держит воркер; пришлось бы добавлять gevent или отдельный сервер.
- *Node.js (Express/Fastify)* — технически подходит одинаково; причин предпочесть его Python-окружению пользователя нет.
- *Go* — больше шаблонного кода для того же объёма CRUD; выигрыш в производительности для задания не нужен.

## Доступ к БД: SQLAlchemy 2 + psycopg 3 + Alembic

- SQLAlchemy 2 даёт явные транзакции и прямой доступ к `with_for_update()`, `postgresql.insert(...).on_conflict_do_nothing()`, `skip_locked=True` — именно те конструкции, на которых держится корректность.
- psycopg 3 — актуальный драйвер PostgreSQL с поддержкой асинхронного `LISTEN/NOTIFY` (нужен для SSE).
- Alembic — стандартные миграции для SQLAlchemy: схема воспроизводится одной командой.
- `email-validator` — нужен Pydantic для типа `EmailStr` (проверка email при регистрации).
- `tzdata` — база часовых поясов IANA для `zoneinfo`; на Windows её нет в системе, а часовой пояс события нужен для окна чекина (R-11).

**Отклонено:** чистый SQL без ORM — больше ручного маппинга; асинхронный SQLAlchemy для всего — усложняет транзакции и тесты без выигрыша для этой нагрузки (асинхронность нужна только для SSE).

## Live-обновления: SSE + LISTEN/NOTIFY

- Требование — счётчик пришедших у организатора обновляется live. Данные идут только от сервера к клиенту, поэтому достаточно SSE.
- `EventSource` в браузере сам переподключается после разрыва (в том числе после перезапуска backend); после переподключения клиент заново запрашивает актуальные счётчики — пропущенное не теряется.
- SSE — обычный HTTP: проходит через Vite-прокси, cookie сессии отправляется автоматически.
- Сигнал об изменении публикуется через `NOTIFY` в той же транзакции, что и чекин/регистрация, и доходит после фиксации — клиент не увидит незафиксированные данные. Работает и при нескольких процессах backend.

**Отклонено:** WebSocket — двунаправленный канал не нужен, нет встроенного переподключения; периодический polling — проще, но «live» с задержкой и лишняя нагрузка; Redis Pub/Sub — лишний сервис, когда PostgreSQL уже это умеет.

## Фоновые задачи: цикл в процессе backend

- Две задачи: (1) напоминания за сутки, (2) «доставка» писем из outbox. Обе — периодический опрос БД (≈ раз в 30 с).
- Расписание не хранится в памяти: кандидаты выбираются по текущему состоянию БД, поэтому после перезапуска пропущенное досылается само (правило R-9).
- Дубли исключены ключами идемпотентности и `SKIP LOCKED`, поэтому даже несколько экземпляров backend безопасны.

**Отклонено:** Celery/RQ + Redis — отдельный брокер и воркер ради двух простых периодических задач; APScheduler — держит расписание в памяти или требует отдельного хранилища, а задачу «досылать после простоя» всё равно пришлось бы решать.

## Почта: заглушка outbox

- Задание разрешает заменить почту заглушкой. Письмо — строка в таблице outbox, создаётся в той же транзакции, что и причина (регистрация, продвижение, перенос). Нет состояния «место дали, а письмо потеряли».
- Страница «Почта (заглушка)» в интерфейсе показывает письма — проверяющий видит билеты и напоминания без внешних сервисов.
- Тесты проверяют «ровно одно письмо» прямым запросом к БД.
- Настоящий SMTP можно подключить позже, заменив только «доставщик»; тогда гарантия станет «как минимум один раз» — это будет отмечено в README.

**Отклонено:** Mailpit/MailHog — реалистичнее (настоящий SMTP), но это ещё один контейнер, а проверка «ровно одно письмо» в тестах усложняется.

## Вход: серверные сессии в cookie

- Учётные записи у всех (решение пользователя). Пароль хешируется `hashlib.scrypt` из стандартной библиотеки — без дополнительных пакетов.
- Сессия — случайный токен в таблице сессий, передаётся в HttpOnly-cookie с `SameSite=Lax`.
- Почему не JWT: JWT требует секретного ключа (его надо хранить и не утечь в репозиторий), его нельзя отозвать при выходе, а `EventSource` не умеет передавать заголовок `Authorization`. Cookie решает все три проблемы.
- API принимает только JSON; вместе с `SameSite=Lax` это закрывает CSRF для локального запуска (ограничение будет описано в README).

## Frontend: React + Vite

- React — один из двух разрешённых вариантов; большая экосистема, привычен большинству проверяющих.
- Vite — быстрый dev-сервер и сборка; его прокси отдаёт `/api` с backend на том же origin, поэтому не нужны CORS и не возникает проблем с cookie.
- Зависимости минимальны: React Router для экранов. Без UI-библиотеки и менеджера состояния — экранов немного, хватает `fetch` и состояния компонентов.

**Отклонено:** Next.js — серверный рендеринг и свой backend-слой не нужны и размывают требование «отдельный backend и frontend»; Vue — подходит одинаково, выбор React — по распространённости.

## Тесты

- pytest + `TestClient` FastAPI (транспорт — пакет `httpx2`: Starlette объявил использование `httpx` в `TestClient` устаревшим) на **реальной PostgreSQL** (отдельная тестовая база) — блокировки и уникальные индексы проверяются по-настоящему.
- Конкурентные тесты — параллельные запросы через пул потоков, у каждого своё соединение с БД.
- Планировщик тестируется вызовом одного шага с подменённым «текущим временем».
- Playwright — E2E с двумя контекстами браузера для проверки live-счётчика (B8).

## Запуск

- Docker Compose: `postgres`, `backend`, `frontend` — одна команда, нужен только Docker.
- В README будет и запуск без Docker (локальные PostgreSQL 16, Python 3.14 + uv, Node.js 20+).
- Секреты в репозиторий не попадают: значения по умолчанию — только для локального запуска, реальные — через `.env` (в `.gitignore`), шаблон — `.env.example`.
