## 2026-10-06 23:21 — Этап 2: регистрация, отказ, лист ожидания, письма (backend)

**Контекст.** Пользователь закоммитил этап 1 (`b2020bd`).

**Задача.** F2–F5, F7 (без счётчика «пришло» — он появится с чекином), B1–B5, B9 и правила R-1…R-6, R-10, R-11 (в части регистрации и отказа), R-15, R-16 из `acceptance.md`.

**Решения.**
- Миграция `0002`: таблица `registrations` (событие, пользователь, нормализованный email, статус, код билета, порядок в очереди, отметки времени), таблица `outbox_emails` (почтовая заглушка), поле `events.schedule_version`.
- Защита на уровне БД: уникальный индекс (событие, email) — B2; уникальный код билета; `CHECK` на допустимые статусы, «у confirmed есть код», «у waitlisted есть место в очереди».
- Регистрация, отказ, продвижение очереди, изменение лимита и перенос выполняются в одной транзакции под блокировкой строки события (`SELECT … FOR UPDATE`, `app/registrations.py`). Решение «место или очередь» принимается внутри блокировки.
- Порядок очереди — значение из последовательности PostgreSQL `registrations_waitlist_seq`, а не время постановки. Отличие от буквы R-4 («время, затем id»): при одинаковом времени (подменённые часы в тестах) реактивированная запись с меньшим id оказалась бы впереди. Последовательность строго возрастает, поэтому восстановленная после отказа запись всегда встаёт в конец. Время постановки тоже хранится — для отображения.
- R-2: повторная регистрация активной записи возвращает её как есть (HTTP 200 вместо 201), без писем. Запись после отказа восстанавливается: свободное место — новый код билета; иначе — в конец очереди. У отменённой записи код сохраняется, чтобы будущий чекин мог ответить «билет отменён»; при постановке в очередь код стирается.
- R-5: отказ из очереди не двигает очередь; повторный отказ ничего не меняет. Отказ и регистрация после начала события — 409.

## 2026-10-08 17:57 — Этап 5: live-обновления экрана организатора (backend)

**Задача.** B8 (счётчики на экране организатора меняются без перезагрузки), G5 (несколько открытых экранов), R-14 (переподключение) из `acceptance.md`.

**Решения.**
- Сигнал об изменении — PostgreSQL `pg_notify('event_changes', <id события>)` в той же транзакции, что и само изменение: регистрация, отказ (с продвижением очереди), изменение события (лимит, перенос), чекин. PostgreSQL доставляет уведомление только после `COMMIT`, поэтому экран не увидит изменение, которое потом откатилось. Работает и при нескольких экземплярах backend: слушатели получают сигнал от любого из них.
- `GET /api/events/{id}/attendees/live` — поток SSE (`text/event-stream`). Каждое событие потока `attendees` — полный снимок экрана организатора (тот же JSON, что `GET /api/events/{id}/attendees`: счётчики и списки), а не разница. Так клиенту не нужно ничего склеивать, и пропущенное уведомление исправляется следующим снимком.
- Порядок: сначала `LISTEN`, потом первый снимок. Изменение между ними не теряется — оно придёт следующим снимком. При переподключении (R-14) клиент сразу получает актуальное состояние, «догонять» историю не нужно.
- Уведомления других событий отфильтровываются по id. Раз в 15 с при отсутствии изменений уходит комментарий `: ping`, чтобы прокси не закрывали поток по таймауту; по нему же backend узнаёт о закрытой вкладке и освобождает соединение `LISTEN`.
- Доступ — как у экрана организатора: 401 без входа, 403 не организатору, 404 нет события. Проверка выполняется в начале запроса с короткой собственной сессией БД, чтобы соединение пула не держалось всё время жизни потока.
- Cookie `ep_session` больше не показывается полем в Swagger (`/docs`): её передаёт браузер, а поле вводило в заблуждение. Поведение входа не изменилось.
- Nginx во frontend-контейнере уже настроен на этапе 0 (`proxy_buffering off`, `proxy_read_timeout 1h`); backend дополнительно отдаёт `X-Accel-Buffering: no`.
- Миграция не нужна.

**Окружение проверок.** Как на этапах 2–4: код в папке проекта, тесты — на копии в облачном окружении агента (Linux, Python 3.14.6, PostgreSQL 16.15). Файлы сверены по MD5 — совпадают все 34 `.py`-файла backend.

**Проверки (выполнены).**
